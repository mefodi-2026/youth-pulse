### Облачные 429: корреляция, а не объединение причин

`cloud-429-correlation.json`: полностью прочитано окно 2026-09-29 15:38–15:43 UTC, 581 запись, без следующей страницы. 161 OPTIONS 204; 90 POST 200; 116 POST 429; 3 POST 400. Все **116/116** trace с 429 имеют связанную запись `Callable request verification passed`: запросы дошли до обработчика, Auth VALID. Сообщений инфраструктурного отказа, quota/rate-limit или capacity в связанных записях нет. Тела callable response в этих журналах отсутствуют.

В развёрнутом join обработчике единственный явный `resource-exhausted` — ветка `failure === 'full'` с «Комната уже заполнена…». Это сильное указание на прикладной отказ, но без тела ответа/исхода транзакции не доказывает заполнение конкретных исторических комнат. Инфраструктурный отказ **до** обработчика для этих 116 запросов исключён; другие источники 429 нельзя объявлять исключёнными только по коду. Эти 429 не сопоставлены с исходным стартовым инцидентом.

Первоначальный `functions/internal`: сохранённый `load-MUV0C6K0.json` показывает один отказ из 30 quiz-регистраций; 29 оставшихся дошли до результатов. В первоначальном локальном запуске наблюдались EPIPE/ECONNRESET между worker-процессами; последующий прогон стандартного эмулятора и тёплого обработчика прошёл с 30/30. Полный исходный worker-журнал не сохранён, поэтому его нельзя задним числом считать доказательством облачной ошибки. `Java heap space` при поздней нагрузке — отдельный сбой локальной RTDB; новый свежий прогон 100/100 прошёл. Ни один из этих локальных кодов не установлен причиной вылета реальных людей.

## Ограничения и путь данных

- `functions/index.js`: создание комнаты сохраняет `maxParticipants: 30`; `joinRoomAsGuest` ограничивает вместимость до 30 и проверяет количество **до** добавления. Ровно 30 разрешены, 31-й получает `resource-exhausted` / HTTP 429. Такой отказ не ломает уже подключённых.
- Предполагаемое число участников 1–30 — отдельная настройка, не обязательный порог запуска. Браузерная диагностическая комната с ожиданием 30 была запущена с одним реальным тестовым гостем.
- Auth создаётся до регистрации; гостевой UID является ключом участника. Регистрация серверная, transaction всей сессии. Повторное подключение возвращает ту же запись; клиент подтверждает чтением своей записи, а не локальным флагом.
- У гостя подписки на publicRoom, безопасный набор вопросов, свою запись и свои разрешённые результаты. Чтение корня чужой/всей сессии в нагрузочном тесте отклонено Rules. У ведущего подписка на всю его сессию.
- Запуск — подтверждённая атомарная запись фазы и публичного состояния; интерфейс затем реагирует на синхронизацию. Проверка фактического состава, а не ожидаемого количества.
- Викторина: один callable на ответ; обработчик читает всю сессию и два набора вопросов, затем пишет multi-location update. На финальном ответе сохраняет итог. Одинаковый повтор сохранённого ответа идемпотентен; конфликтный повтор последовательно отклоняется политикой. Одновременная отправка разных вариантов одним UID до первого commit отдельно не проверена: предварительное чтение + update не является транзакционной блокировкой.
- Диагностика: один SDK multi-location update ответа, индекса, статуса и lastActivity, с проверками Rules; callable оценки не используется. Потеря сети не означает завершение.
- Неактивность комнаты — 10 минут. Порог 30 не является порогом тарифа RTDB: общие сервисные пределы описаны в [официальной документации](https://firebase.google.com/docs/database/usage/limits). Они не заменяют измерения именно этого проекта.

## Воспроизведение стенда

1. Установить зависимости корня и functions. Java 21+, Firebase CLI 15.32.1; Node 24 использовался в этом прогоне (production Node 20).
2. `firebase emulators:start --config firebase.audit.json --only auth,database --project demo-youth-pulse-audit`.
3. `node scripts/audit-callable-server.cjs` — исходная вместимость; для отдельного процесса порт 5003 задать `AUDIT_CAPACITY=100`, `AUDIT_SERVER_PORT=5003`.
4. `AUDIT_FUNCTIONS_PORT=5002` и `node scripts/audit-load.mjs`. Для настоящего каталога нужен локальный JSON без персональных данных и `AUDIT_CATALOG`; иначе quiz-фикстура синтетическая и так помечена. `AUDIT_PACK`, `AUDIT_SIZES`, `AUDIT_STRATEGIES`, `AUDIT_MODES` сужают сценарий.
5. `node node_modules/vite/bin/vite.js --config vite.audit.config.ts --configLoader runner` — отдельная локальная браузерная конфигурация, не применяется нормальной сборкой.
6. Auth-данные локального ведущего генерирует `scripts/audit-browser-fixtures.mjs`; файл `audit-results/browser-fixtures.json` игнорируется Git. `audit-clean-fixtures.cjs` удаляет только локальные нагрузочные комнаты с проверяемыми признаками, не браузерные комнаты.

Syntax checks и существующие architecture/participant routing/quiz idempotency contracts пройдены. Они не заменяют незавершённые облачные и мобильные проверки.
